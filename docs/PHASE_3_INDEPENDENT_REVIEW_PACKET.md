# Phase 3 Independent Review Packet

**Status:** Ready for assignment once the EXP-0003 Draft field table is complete enough for clean-room interpretation  
**Rebased:** 2026-08-13 against consolidated `main`  
**Audience:** independent implementers, format reviewers, security engineers, storage engineers  
**Tracking:** issues #12 and #76

## Goal

Obtain evidence that the immutable-page successor is independently understandable and that reference implementations have not merely reproduced one shared misunderstanding.

A review is independent only when the reviewer can challenge the specification, derive expected behavior without relying on reference implementation internals, and report disagreements as findings rather than adapting silently to existing output.

The preferred outcome is a separately maintained implementation in another language or repository. A documented clean-room external review may satisfy the gate only if it produces reproducible parser/writer/vector evidence and dispositions material findings.

## Independence boundary

Review should target the proposed EXP-0003 specification and authoritative corpus, not the current 64-bit/88-byte research microformat merely because that code already exists.

The consolidated `main` implementation is evidence and a comparison target. It is not the normative source for undocumented behavior.

## Review tracks

At least one reviewer should cover each track. One person may cover multiple tracks, but an independent implementation should not be maintained by the same authors as the reference writer.

### 1. Wire specification

Review:

- bootstrap, object, page, snapshot, and footer field boundaries;
- integer byte order and canonical encodings;
- object identifier ordering;
- primary locator and internal child-reference layouts;
- domain-separated digest preimages;
- exact padding and reserved-byte rules;
- object, page, snapshot, and commit identity scopes;
- page occupancy, split, redistribution, merge, and root rules;
- canonical batch semantics;
- active-root and exact-end rules;
- parent snapshot and previous-footer linkage;
- behavior for unknown required and optional capabilities;
- all undefined, contradictory, or host-language-dependent behavior.

Deliverable: annotated specification findings with proposed replacement language for every ambiguity.

### 2. Independent parser

Implement, in a separately maintained codebase or clearly isolated package:

- exact-end strict validation;
- active object inventory;
- authenticated lookup and absence;
- linked-history validation;
- bounded recovery candidate reporting.

The parser must not call the Rust reference codec or import its private constants. It may consume published specification tables and authoritative vector files.

Deliverable: implementation location, supported assurance modes, resource-limit model, and vector results.

### 3. Independent writer

Generate at least:

- minimal genesis;
- multi-leaf genesis;
- replacement append with historical page reuse;
- insertion without split;
- insertion with leaf split;
- recursive internal split and root-height increase;
- deletion without underflow;
- left/right borrow boundary cases;
- deletion merge, recursive underflow, and root collapse;
- canonical mixed deterministic batch.

Deliverable: generated byte identities and a mismatch report against authoritative vectors.

### 4. Security review

Challenge:

- checked arithmetic and conversion boundaries;
- allocation and source-work accounting;
- forged and overlapping physical ranges;
- page cycles, duplicate references, and mixed-age traversal;
- validation order and reauthenticated inner-layer mutations;
- exact-end versus recovery separation;
- history and recovery candidate authority;
- mutable remote source behavior;
- unknown extension preservation and rewrite;
- semantic compaction dependency completeness;
- spill confidentiality, cleanup, restart, and publication state;
- rollback/freshness non-claims.

Deliverable: threat-to-test matrix and severity-ranked findings.

### 5. Storage and transport review

Evaluate:

- range request count and byte transfer for lookup, full validation, history, recovery, and rewrite;
- strong version-token assumptions across HTTP and cloud object stores;
- retry, cancellation, authentication-refresh, and deadline semantics;
- local filesystem no-overwrite and durability claims;
- cross-filesystem publication;
- descriptor-limited sorting and staged merge;
- encrypted spill policy and restart qualification.

Deliverable: platform-specific limitations and tests required before production claims.

## Normative independence rules

Reviewers should derive behavior from the proposal and specification first. Reference code may be inspected only after an initial interpretation is recorded for the relevant section.

For each mismatch, classify:

- specification defect;
- reference implementation defect;
- independent implementation defect;
- vector defect;
- unresolved interpretation requiring FCP amendment.

Do not change independent code merely to match a vector before recording why the mismatch occurred.

## Required authoritative vector set

The handoff must include:

- exact valid genesis, append, multi-level, and mixed-operation vectors;
- deterministic recipes for large or repetitive cases;
- occupancy boundary vectors using the accepted EXP-0003 capacities;
- invalid vectors targeted at every fixed field and validation layer;
- interrupted publication around snapshot/footer publication;
- valid equal-sequence forks and broken linkage;
- recovery candidates including multiple valid prefixes;
- semantic-compaction/profile boundaries for known, missing, cyclic, and unknown dependencies;
- source traces for version change, malformed range response, cancellation, authentication refresh, and deadline;
- spill/publication fault traces.

Every stored or generated case must pin its byte length, cryptographic identity, expected assurance result, and rejection concept without overfitting to one implementation's exception type.

## Recommended clean-room sequence

1. Read FCP-0003 and `spec/experimental/UCOF-EXP-0003.md` only.
2. Record ambiguities and an initial field/digest/algorithm table.
3. Implement the smallest exact-end parser.
4. Run the valid minimal genesis vector.
5. Add invalid vectors one validation layer at a time.
6. Add authenticated lookup and absence.
7. Add history and recovery as distinct APIs.
8. Generate at least one nontrivial vector independently.
9. Add structural mutation writer cases.
10. Compare with reference identities and record all mismatches.
11. Inspect reference code only where needed to diagnose an already-recorded mismatch.
12. Submit findings using the template below.

## Acceptance gates

Independent review is sufficient for the Phase 3 exit gate only when:

- every blocker and high-severity finding is resolved or explicitly accepted with rationale;
- specification ambiguities that affect bytes or assurance are amended through the FCP process;
- at least one independently generated nontrivial EXP-0003 file is accepted by the reference parser;
- at least one reference-generated nontrivial EXP-0003 file is accepted by the independent parser;
- both implementations reject the selected layer-targeted invalid corpus for compatible reasons;
- mutation cases agree on byte-significant occupancy/split/delete/batch behavior;
- resource limits and exact-end/recovery boundaries are demonstrated independently;
- the review artifact remains publicly reproducible.

A review that only reads code, runs the existing Rust tests, or confirms unit-test counts does not satisfy this gate.

## Current known limitations reviewers should not overlook

- FCP-0003 remains Draft and EXP-0003 is not allocated;
- the proposed 128-bit identifier / 64-byte locator layout intentionally differs from the current research microformat;
- authoritative EXP-0003 vectors do not yet exist;
- maintained HTTP/cloud adapters and native asynchronous cancellation remain open under #10;
- production spill encryption and platform durability qualification remain open under #11;
- semantic dependency behavior requires profile/application rules rather than core guesses;
- no file integrity or stable-source mechanism establishes freshness without trusted external state;
- implementations maintained in the same repository are not sufficient independence evidence by themselves.
